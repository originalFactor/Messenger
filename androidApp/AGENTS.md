# androidApp — Android application shell

Thin `com.android.application` shell over `shared` (AGP 9 built-in Kotlin + `kotlin.compose` + `kotlin.serialization` — do NOT apply `kotlin-android`). Holds `applicationId`, `versionCode`/`versionName` (from the root `VERSION` + commit count), `signingConfigs` (keystore `keyring/messenger-release.jks`, env `KEYSTORE_PASSWORD`/`KEY_ALIAS`/`KEY_PASSWORD`), `buildTypes`, `buildFeatures { compose = true }`, and application-level `res/`.

- `MainActivity.kt` — the Compose entry point.
- `MessengerApplication.kt` — constructs the Kotlin/Room `AppBackend` through `KotlinAppBackendFactory`, injects it into `AppContainer`, and installs the platform image loader and Wear service.
- `RuntimeShellClient.kt` — AIDL client registered as `ShellRuntimeRegistry.bridge` at startup; routes shell/workspace calls to the `:runtime` companion (absent companion ⇒ tools disabled, see `runtime/AGENTS.md`).
- MCP sessions retain the exact Runtime Binder that accepted their start. Binder death or service disconnection reports an unverified stop; never reconnect and treat the replacement Runtime as proof that the original child exited. Exit callbacks and Binder-stop completion are both required before shutdown succeeds.
- Android ACP process transport requires Runtime ACP protocol version 2, which binds input and stop to the callback Binder from the accepted start; older companions must be updated before starting ACP. Binder death or service disconnection becomes a process error, and a failed stop is surfaced even during cancellation. Cleanup cancels input and starts direct-child stop before joining a potentially blocked Binder write. It reports unverified if stop, exit callback or input completion is missing after bounded waits; a blocked Binder call can remain in flight after that report. Runtime retains the old generation until its admitted input returns. A rejected start is never stopped by ID, while a failed start call reports an unverified start outcome. Unexpected nonzero exits report the exit status, while an exit following an explicit stop is treated as expected. Neither a stop return nor an exit callback proves arbitrary detached descendants have stopped.
- The isolated Kotlin turn host can use synchronous Runtime workspace AIDL through a Messenger-process in-memory tracker. Glob/read/edit/create use the existing synchronous methods; grep is exposed only if the Runtime advertises the new safe-grep protocol. A normal return records STOPPED in the same connection generation; disconnect, Binder failure and process restart make the outcome UNKNOWN. The host keeps cancellation pending until the call returns. Unknown outcomes keep their turn reservation until verified offline recovery. Older Runtime versions without the safe-grep capability do not expose grep; terminal requires a separately verified lifecycle. Runtime’s appended tracked protocol remains disabled and its journal must never be accepted as stop proof. This path is not yet connected to production.
- Projectless chat workspaces are created through Runtime AIDL in its cache so shell and file tools can reach them across app UIDs; retain the matching AIDL method in both modules.
- `src/main/AndroidManifest.xml` — the FULL application manifest (the `shared` androidMain one is a minimal root): activities/services/providers, `enableOnBackInvokedCallback` (predictive back), `windowSoftInputMode="adjustResize"` on the chat activity, and the FQN service declaration `cc.ptoe.messenger.data.wear.MobileHttpServer` (class lives in `shared`). `aidl/` carries copies of `IShellService`/`IShellCallback`/`IMcpCallback` and `ToolResult` (same FQNs as `:runtime`; keep the AIDL files and Parcelable implementation in sync) plus `<queries>`/`<uses-permission>` for the companion.
- R8 + resource shrinking are ENABLED for release (`isMinifyEnabled = true`, `isShrinkResources = true`) with rules in `androidApp/proguard-rules.pro`. The kept surface is: manifest components, the FQN-declared `MobileHttpServer`/`MobileWearChatHandler` from `shared`, ucrop's activity, kotlinx.serialization's serializer lookup, Coil/Ktor service-loader targets, OkHttp's optional TLS providers and reflective ViewModel constructors. Markdown/LaTeX rendering is the `llm-typewriter` submodule; there is no `:renderer-android`.
- ABIs come from the root build script and are applied as per-build-type `ndk.abiFilters` (NOT `splits.abi`, which is global; and NOT `defaultConfig`, whose list AGP unions into every build type): release `ext["releaseAbis"]` = `arm64-v8a`, debug `ext["debugAbis"]` = `arm64-v8a` and `x86_64` for physical devices and Android Studio AVDs. Debug compiles both Rust targets. Override with `-Pmessenger.abis` / `ANDROID_ABIS` (release) and `-Pmessenger.debugAbis` / `ANDROID_DEBUG_ABIS` (debug).

```bash
./gradlew-cli :androidApp:assembleDebug
./gradlew-cli :androidApp:assembleRelease   # R8 on; one APK containing the selected release ABIs
./gradlew-cli :androidApp:lintDebug
```

- Interactive learning applications use the `shared` Android WebView host and origin-restricted AndroidX WebKit message listener. Keep the generated sandbox separate from the trusted wrapper; no broad JavaScript interface or Core credentials. The host blocks direct network/navigation and destroys WebViews on disposal. Learning packages and image exports use system document pickers; do not request broad storage access.

- For third-party ACP Agents, the main app bridges Core's local ACP process streams to `IShellService` in the Runtime companion. The main app does not launch Runtime-installed executables in its own UID.

- A disposable package-upgrade probe on an Android API 37 x86_64 emulator (target SDKs 28 and 36, ordinary `adb install -r`) observed the updated package's main process, secondary process, and direct `setsid` child disappear, while a separately installed Runtime-like UID and its direct `setsid` child stayed alive. This is one emulator observation, not a guarantee for other devices, install modes, or detached process trees. In particular, package replacement alone cannot prove that Runtime or ACP work has stopped; an Android Room cutover must independently fence and verify those workers and all old Core/source users before opening the store and again before releasing its owner.
- A separate API 37 x86_64 device test observed that a Runtime child under the companion UID could not read one app-private fixture, even when that file was world-readable; the main app could read it. This tests that fixture's directory access only and does not prove asset isolation on other devices or that old workers have stopped.
- `AndroidWorkspaceCandidateStager` is an unconnected archive-import experiment. An explicit caller supplies an authorized open archive descriptor, and the app stages it under its own UID without publishing it as a live workspace or modifying the source. Old Core code sharing that UID can still access the candidate. The archive is unauthenticated and may combine different source moments; unsupported entries and metadata losses must be disclosed before any future user import. A separate Runtime UID cannot use the candidate directly, and no new Runtime UID or production migration is installed. Runtime and Android app compile the same small archive parser from `runtime/workspace-transfer-shared`, without a new Gradle module.
- [Android Core cutover ownership](docs/CORE_CUTOVER_OWNERSHIP.md) records why the existing Core stop, SQLite lease and Runtime direct-child tracker are incomplete proofs, and the lifetime guarantees required before connecting the Room host to production.

- Android push uses the supplied JPush 6.3.1 / JCore 5.6.0 and FCM bridge AARs in `libs/`; `google-services.json` configures the matching Android Firebase app. `PushSetup` initializes JPush and enables Firebase Messaging only after the user opts in, and `MainActivity` requests Android 13 notification permission. Declining defers the prompt until the next launch. `MessengerApplication` skips Core startup in JPush's `:pushcore` process. The SDK's optional location, phone and broad package access permissions are removed from the merged manifest. Firebase delivery also requires configuring the FCM service account in the JPush console. The supplied JCore AAR includes arm64-v8a native code only; test x86_64 behavior separately before relying on emulator push.

- Android registers its consented JPush registration ID against the current Cloud session through Core, both on sign-in and ID rotation; the server scopes delivery to active sessions and invalidates registrations on logout.

- `AndroidForegroundTasks` installs the shared task lifecycle hooks and polls Core `/activity`; overlapping UI work and Core-owned tasks retain `TaskForegroundService`. It uses an ongoing special-use foreground notification and a bounded, renewed partial wake lock only while tasks are active. The scheduled-task setting persists an explicit opt-in for keeping the service running while idle; restore is attempted only from a visible activity or an OS service restart. Android can reject background starts, restrict network or kill the process, and Doze may delay scheduled work; foreground service is not a guarantee. Notification permission/channel availability is checked when enabling the setting. The manifest declares the special-use subtype and wake-lock permission.

- `LocalTaskNotifications` listens to Core's task status events and posts generic completion, failure and approval notifications through a separate local channel, independently of JPush. Notifications are keyed per task; approval resolution and cancellation clear stale prompts. Tapping a notification opens the app. Android notification permission and process lifetime still apply.

- Android notification taps use the explicit `cc.ptoe.messenger.OPEN_PUSH` activity action with validated conversation/device IDs. Local task notifications use distinct immutable pending intents; Desktop JPush opens the owning device conversation through the shared remote-control view. External notification data only selects a route and never authorizes commands.

- Isolated Kotlin scheduled-task notifications use `KotlinScheduledTaskEvents`; Core remains the production scheduler.
