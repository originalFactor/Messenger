# core — Rust Agent Core and local API

`core/rust` is a Cargo workspace (resolver 2, release LTO + strip) with 9 crates. `core/bindings` and `core/bindings-desktop` build the native library and generate the lifecycle-only UniFFI surface used by Android/Desktop. Android, Desktop, and the Python TUI use the loopback `/api/v1` REST/SSE service in `messenger-http`.

## Crates

- `messenger-core` — agent loop (`run_chat_turn`), parts codec, context math, title helpers and conversation policy.
- `messenger-llm` — four wire protocols (`chat`/`responses`/`messages`/`interactions`), streaming parser, tool-call accumulation, usage stashing, request builder and explicit OpenAI-compatible Images generation adapter.
- `messenger-tools` — built-in terminal/workspace declarations and per-tool policy.
- `messenger-store` — SQLite schema v8 (v7 cache-write rates; v8 independent local learning library), typed CRUD, store events, sync/kv bookkeeping and legacy Room import.
- `messenger-sync` — paged delta sync, cloud auth/session handling, avatar caching, market/card APIs and model discovery.
- `messenger-mcp` — JSON-RPC MCP client, configuration codec, pluggable stdio / SSE+HTTP transports and tool lifecycle. Kotlin also retains its platform MCP manager; do not assume this crate replaces the native UI inventory.
- `messenger-remote` — cross-device project routing: `RemoteHub` holds the per-device cloud relay SSE connection (`/api/remote/*`), tracks which devices are online, forwards workspace tool calls to the project's owner and validates/executes inbound ones. Contract: `crates/messenger-http/docs/REMOTE.md`.
- `messenger-http` — axum loopback REST/SSE server covering CRUD, pagination, chat turns, tool results, cloud sync and cancellation. Its `messenger-core-server` binary is the TUI’s lifecycle bridge. It opens a dedicated SQLite store under an advisory lock, ensures the default Agent exists before serving, writes the loopback URL and bearer token to the child’s stdout pipe, and shuts down on stdin EOF.
- `messenger-ffi` — lifecycle-only `CoreHandle.open`, `start_http_server`, `HttpServerHandle.local_addr/token/stop` and `CoreError`.

The Rust core does not contain a Document Engine, Markdown parser, LaTeX renderer, syntax highlighter, browser boundary or TUI crate. Android/Desktop render Markdown, code and LaTeX in Kotlin with `cc.ptoe:llm-typewriter`.

## Local API boundary

- `messenger-http` owns request validation, default-Agent protection, model-required checks and cloud error mapping.
- `/cloud/builtin-models/sync` provisions Messenger Cloud AI from the saved account before fetching its catalog. Clearing the Cloud session removes that provider and its models. Public Provider/model CRUD (including enabled and reparenting) rejects the built-in catalog with 409 `builtin_catalog_read_only`; internal provisioning/sync writes remain allowed. Manual native Sync uses this endpoint, importing authoritative Messenger Extended Models Protocol `/v1/models` metadata and rates without local overrides, stale-rate retention or models.dev enrichment.
- `/cloud/conversations/push` uploads standalone TUI conversations without applying Cloud data. It stores the account/server binding and last uploaded digest/version, checks for newer Cloud changes before updates, and maps local-only Agent IDs to the Cloud default. Keep provider credentials and unrelated entities out of these uploads.
- Model rows persist capability metadata separately from explicit overrides. Provider discovery reads Messenger extensions from `/models`. TUI discovery opts out of models.dev; Python `tui/messenger_tui/model_metadata.py` fills missing capabilities from pi-catalog. Built-in models persist only Cloud-supplied capabilities.
- Tool policy stays in Rust. Kotlin and the TUI execute platform tools and post results to `/turns/tools/{callId}/result`. The TUI's `/tools` command persists conversation overrides; its local executor uses the trusted project's workspace.
- Dropping the chat SSE cancels the turn token, wakes a pending tool host and finalizes partial rows.
- **`ServerHandle::stop` must close the endless streams**: axum's graceful shutdown resolves only after every in-flight response ends, and `/events` never ends on its own — so `ServerHandle`'s `CancellationToken` is handed to `ApiState`, whose `/events` handler wraps the feed in `ShutdownStream`. Without that, `stop()` never returns and the desktop app freezes on window close. Any future long-lived (SSE/websocket) route needs the same treatment.
- **`ApiState` is `Clone`, so its cleanup cannot be in `Drop`**: axum clones the state per request, and the first dropped clone used to `unsubscribe` the store listener, silently killing the change feed for every later subscriber. The registration lives in `StoreFeed`, held through an `Arc`, so it ends with the last clone.
- Contracts: `crates/messenger-http/openapi.yaml` and `crates/messenger-http/docs/SSE.md`.

## Remote projects

- A project's `deviceId` names the device that owns its workspace. Its conversations' workspace tools (terminal/glob/grep/read/edit/create) execute on that device; only tool calls cross devices, the turn itself stays on the initiator.
- A remote-owned project is *unavailable* while its owner (or this device) is not connected to the relay: `POST /conversations/{id}/messages` returns 409 `project_unavailable` before any row changes. Project responses carry `owner` + `available`.
- The owner's `messenger-remote` hub validates inbound calls (owned project, built-in workspace tool, writable conversation for `edit`/`create`) and hands them to the local platform client through the `/events` feed (`remoteTool`/`remoteToolCancelled`); the client posts results to `/turns/tools/{callId}/result`.
- The cloud server (`server/`, `lib/remote-hub.ts` + `/api/remote/*`) is the relay and persists `deviceId` on project documents. Its online set is in-process memory, so the server must run as a single instance; signed out or unreachable relay = hub idles/backs off and remote-owned projects stay unavailable.

## Versioning

`messenger-core` reads the repository-root `VERSION` and exposes the semantic name plus git commit count. The TUI packaging workflow reads the version from `messenger-core-server --version`. Rust never uses `CARGO_PKG_VERSION` as the product version. Unlike Gradle, the current build script accepts non-empty version text without a semantic-version check and warns/falls back to `0.0.0` when VERSION is missing/empty; its commit count falls back to 0 without git. TUI release packaging validates the reported semantic version; release tags must still match root VERSION.

## Native bindings

- `:core-bindings` (`core/bindings`) builds host `messenger-ffi` + `uniffi-bindgen` with profile `bindgen` for lifecycle binding generation. Its per-build-type cargo-ndk tasks package the selected Android ABIs using Rust `--release` even for an Android debug variant.
- `:core-bindings-desktop` (`core/bindings-desktop`) generates the same surface and packages the host cdylib from profile `bindgen` as a JNA resource. This profile is shipped on Desktop: `strip = "none"`, LTO off, 16 codegen units. Keep metadata symbols intact for UniFFI on ELF; it cannot generate bindings from a stripped release library.
- Both binding modules share the Cargo workspace, with Gradle task ordering to avoid concurrent host-output mutation. Maintain their generated-source and native-resource wiring when changing build tasks.

## Default Agent preset

`messenger-store::DEFAULT_AGENT_DESCRIPTION` / `DEFAULT_AGENT_PROMPT` (`src/default_agent_prompt.txt`) hold the creation-only preset shared by the standalone Core seed and login local-data baseline. Keep the text aligned with Kotlin `Agent.DEFAULT_AGENT_DESCRIPTION` / `DEFAULT_AGENT_PROMPT` and Cloud `lib/default-agent.ts`. Seeding never overwrites an existing default, binds a model or enables tools. The exact unmodified preset does not count as local user data at login; edited descriptions/prompts, renamed Agents and model bindings retain the existing local-data detection.

## Local learning workbench

- `messenger-store/src/learning.rs` owns typed `LearningRecord` envelopes (`content.kind`: course, knowledgePoint, item, material, plan, task, reviewCard), immutable content revisions, review states and immutable attempts. Schema v7 migrates to v8 with independent `learning_*` tables. IDs and UTC timestamps are stable; version 0 creates, current version updates, and deletes require the current version. Relations validate referenced kinds, course ownership and knowledge-point cycles; referenced records must be archived or have their dependents removed before deletion.
- Learning source snapshots and owned asset IDs are independent of ordinary/ACP chat rows; never add chat foreign keys or store chat-cache paths as owned materials. Missing ordinary chat/message links are detached on reads while snapshots remain. Cloud chat replacement preserves learning tables; explicit `/local-data` cleanup calls `clear_learning`.
- `messenger-core/src/learning.rs` owns offline `sm2-v1`: feedback again/hard/good/easy maps to quality 1/3/4/5, ease floor 1.3, UTC-day intervals and an injected clock. `submit_review` atomically checks item/state versions, stores the exact item snapshot and updates the schedule. Submission IDs are globally idempotent; a duplicate with different input conflicts. Paused/archived cards reject new attempts. Editing an item never rewrites review history; no tool or webpage may assign formal review ratings.
- `messenger-http/src/learning.rs` adds authenticated `/learning/overview`, `/learning/records/:kind[/:id]`, `/learning/reviews/:id/{state,submit,attempts}`, `/learning/settings`, and metadata-only `/learning/export`, `/learning/import/preview`, `/learning/import`. Lists support search/course/knowledge-point/tag/archive/due filtering and offset/limit pagination (maximum 200). Metadata packages are versioned JSON including records/revisions/states/attempts; previews validate in a rolled-back transaction and commits reject ID collisions. These metadata endpoints explicitly omit external asset/artifact bytes. Full resource bundle adapters can call `import_learning_with_local_kv` to commit learning rows and restricted `local_asset:`/`artifact:` KV entries together after staging resource files.
- Reserved workspace-free `messenger_learning` supports overview/list/get/upsert only. `learning_tools_enabled` defaults off, independent of workspace writability; Core turn/ACP policy must also authorize declaration and execution. The executor rechecks the live feature switch. Upserts return compact summaries and versioned `learningRecord` structured references; scoring and deletion remain user API operations. Learning mutations emit existing `Other` store events with `learning:<id>` (or `learning:*`) IDs, so clients re-query authority without adding these entities to Cloud sync.

- HTTP learning writes validate and pin independently owned source/material assets and verify artifact references under the domain/asset mutation gates. `upsert_learning_with_local_kv` commits owner metadata with the new learning revision; a version conflict cannot leak a resource pin. The Core-owned learning executor is asynchronous and receives `&ApiState` to share this path. Retain resource ownership for immutable revisions and attempts when a live record changes. Explicit deletion uses `delete_learning_with_local_kv` under the same gates to remove the record and its own content revisions and release its asset owners atomically; keep other owners and assets needed by retained review-attempt snapshots, and start the 24-hour unreferenced grace period only when no owners remain.
- `messenger-http/src/assets.rs` owns content-addressed private resource files and `local_asset:` KV metadata. Explicit ownership survives chat/Cloud replacement; imports stage/verify/rename before metadata commit. Downloads validate and pin public HTTPS destinations, recheck redirects, reject private/reserved addresses, and bound time/bytes. GC is explicit, protects current/historical learning/artifact/image bindings, and waits 24 hours after unreference; full local cleanup removes owned bytes. Detailed routes and limits: `crates/messenger-http/docs/ASSETS.md`.
- `messenger-http/src/image_generation.rs` persists explicit BYOK `local_image_profile:` and durable `local_image_job:` records. `image_generation_enabled` defaults off. The `messenger_generate_image` tool and user job API use the same idempotent request service; missing/invalid profile/provider/model/key fails before paid-job creation. Never infer Images API support from chat modality metadata, switch endpoints/providers, or automatically resubmit ambiguous/cancelled/unknown outcomes. A cancelled provider request may already have incurred a charge. Full cleanup cancels image work before clearing resource files. Portable asset provenance uses `provenance:` with sanitized prompts/model/parameters/times/usage, excluding credentials, provider endpoints and runnable job state.
- `messenger-http/src/artifacts.rs` owns `artifact:` records with complete immutable text-file revisions, explicit resource maps, versioned user state and requested/approved HTTPS domains. Resource paths use portable ASCII letters/digits plus `_./-` only, matching the native hosts; reject unrenderable filenames before saving or importing a revision. Reserved `messenger_artifacts` is workspace-free and gated by initially disabled `artifact_tools_enabled` plus effective policy. Native hosts authorize execution through `/artifacts/{id}/authorize-run`; imported artifacts require fresh device trust and network grants. Generated code never receives Core credentials. The trusted host handles the narrow state/fetch SDK; Core rejects untrusted state/fetch writes, stale state formats and optional stale revision IDs. Egress supports only approved public HTTPS443 GET/POST, pinned public addresses, no redirects/proxies, bounded UTF-8 responses, and no ambient cookies/provider secrets. Browser sandbox/input/lifecycle behavior still requires real platform validation; API tests do not establish Desktop/Wayland/browser compatibility.
- `messenger-http/src/learning_bundle.rs` exposes `/learning/package/{export,preview,import}`: versioned JSON containing learning metadata, verified base64 assets, artifact revisions/state and optional sanitized generation provenance. Limits: 96 MiB JSON, 64 MiB decoded assets, 10000 assets and 1000 artifacts, plus learning limits. Preview is read-only; commit stages bytes then atomically writes learning rows and restricted `local_asset:`/`artifact:`/`provenance:` KV metadata. Conflicting learning/artifact IDs reject the import; matching content hashes merge valid owners. Imported network/execution grants reset. Credentials, Provider/profile configuration, paid job state, absolute paths and temporary capabilities never enter portable packages.

## Testing / CI

- `cargo test --workspace` is the workspace verification; `cargo test -p messenger-http` runs the API contract suite.
- The current GitHub workflows compile/package native clients; they do not run `cargo test` or the TUI test workflow automatically. Run the relevant tests locally.
- Native client builds use cargo-ndk for Android and host Cargo for Desktop. There is no Web/Wasm build.

## ACP and device control

- The stable ACP v1 Agent and Client adapters live in `messenger-http`. Desktop exposes the local bearer-protected ACP socket through the `messenger-core-server acp --connect` stdio adapter. The product-facing commands reuse Core turn admission and persisted conversation rows.
- Cloud device control only accepts sessions in workspaces owned by the host. Local Messenger commands still support projectless sessions; creating third-party ACP sessions requires a local-owned project. The catalog includes each session’s project ID and update time, including device-local ACP sessions. Device-owned Messenger turns and native chat share one per-conversation reservation. Send, retry, and regenerate check model and project availability before mutation. Third-party sessions keep a device-local transcript and resume by advertised ACP capability.
- `messenger-remote` carries control requests over the existing account relay. Device opt-in is scoped to the cloud server and account. Disconnect or revocation cancels the owning control request.
- Protocol and setup: `crates/messenger-http/docs/ACP.md`, `REMOTE.md`, `SSE.md`, and `openapi.yaml`.

- **Model rates (schema v7)**: `StoredModel.cache_write_rate` persists in nullable `models.cacheWriteRate`. Existing stores migrate with NULL (unknown); explicit zero remains free. Carry the fourth leg through Messenger `/models` DTOs, discovery, built-in Cloud sync and Cloud model document conversion. Kotlin maps it to `ChatModel.cacheWriteRate`.

- **ACP configuration and native chats**: control settings profiles have optional `description` and `enabled` (legacy default true). GET seeds disabled Codex / Claude Code / OpenCode stdio templates once using `acp_templates_seeded`; deleting a template is permanent. Local ACP transcripts project into `/conversations` and project lists without SQLite/Cloud sync rows. Rename/delete are supported; ACP agent/workspace bindings stay fixed, and deletion during a turn returns `turn_in_progress`. Native chat routes ACP IDs through the control command stream. `store {kind: acp|mcp}` loads authenticated Cloud `/api/integrations/catalog` through `SyncEngine::with_session`, including terminal session expiry. Remote control still requires host-owned workspaces and the account-scoped opt-in.

- **ACP session settings**: `sessionSettings` / `setSessionConfig` reserve an ACP session, read new/load/resume options and mode notifications, and forward Agent-confirmed grouped select/boolean config changes or legacy modes. Never infer Permissions or commit a requested value before the Agent confirms it. Cancellation/timeout discards ambiguous workers. Live and replayed tool/thought events are stored on local transcript rows; native history keeps full rows, while remote relay history remains bounded.

- **ACP composer protocol**: local control `prompt.content` carries ACP text/image/embedded-resource blocks. `steer` forwards `_session/steering` while a prompt is active, uses `promptRequired` on idle, and persists injected input in the owning turn. Session snapshots carry available commands and context usage. Never start an unowned fallback turn or silently retry a rejected steer.

- **ACP MCP setup**: the local platform catalog includes enabled MCP configurations in memory. Native Core waits for the first explicit MCP catalog before starting or restoring an ACP worker; device-owned Messenger turns with tools also wait for the initial `toolsReady` publication after enabled server connection attempts finish. Cancellation, shutdown and a timeout (10 seconds for configuration, 75 seconds for tool discovery) end the wait, while model-required remains immediate. Standalone Core starts with an empty ready catalog and does not wait for a native client. New, resumed and loaded ACP sessions receive enabled configurations through ACP `mcpServers`; unsupported SSE produces an error. Running workers retain their session configuration until restarted. The catalog may contain credentials and must not be persisted or exposed to remote control.
- **Agent Skills**: `messenger-http/src/skills.rs` owns the device-local `agent_skill:<name>` KV catalog and bearer `/skills` CRUD + `/skills/validate` import-preview routes. YAML frontmatter uses `serde_yaml_ng`; packages preserve UTF-8 text and base64 binary resources (128 files, 1 MiB/file, 4 MiB total decoded bytes, 26 MiB JSON request limit). Native/control Messenger turns include enabled name/description JSON metadata only when effective tool policy allows the reserved Core-owned `messenger_skills` reader. The reader loads bundled text on demand; binary reads fail explicitly. Never execute imported scripts, grant permissions from `allowed-tools`, sync packages to Cloud, or inject skills into title generation. Local directory import is not exposed; clients submit validated package bundles and can preview before saving. `skills/remote.rs` adds bearer POST `/skills/remote/discover` and `/skills/remote/preview` (`{source,path?,ref?}`): public GitHub shorthand/repo/tree/blob links and public Git smart-HTTPS sources, with canonical source + immutable commit ref returned for selection. GitHub resolves a selected directory through shallow trees before fetching its bounded recursive tree and blobs; other hosts use bounded shallow Git wire requests through existing reqwest/rustls and minimal gix pack/object readers. Never use a Git process, ambient Git config, credentials, hooks, checkout, submodules or LFS execution. Remote previews do not save; they preserve binary assets, reject symlinks/submodules, exclude nested skill packages/.git, and reuse package validation. Limits include 90 seconds overall, 32 MiB wire response, 8 MiB GitHub tree, 20000 entries/objects, 32 levels and 128 candidates. Discovery reports invalid sibling metadata in explicit `{path,message}` warnings while retaining valid candidates; preview always validates strictly. No silent retries or redirects.
- **Agent delegation**: device-local `mcp_agent_delegation_enabled` defaults off; `/mcp/agent-delegation` controls the Core-owned `messenger_agents` tool for Messenger turns. Calls create a separate conversation, propagate cancellation and workspace mode, and child Messenger turns cannot delegate further. ACP delegates require a local project and writable mode because ACP agents control their own tools; permission prompts cannot be approved by the caller and are cancelled and reported.
- **ACP Skills and delegation gateway**: MCP-capable workers receive a per-worker loopback MCP server with a random capability URL (`Messenger Skills`, or `Messenger Agents` when delegation was enabled at startup), using advertised SSE/HTTP. The `messenger_skills` reader is provisioned even for an empty catalog, and each prompt carries current enabled discovery metadata separately from the stored local user row. Calls require the owning active turn and close with the worker/turn; disabled/deleted Skills fail at read time. New/load/resume share this setup. An enabled catalog with no supported transport fails visibly, including a catalog enabled after worker startup. Delegation has an immutable worker capability in addition to its live global setting: delegated workers receive only the Skills reader, including after restoration, and cannot acquire delegation when settings change. Disabling delegation blocks subsequent calls; enabling requires a new or restarted worker. Do not persist gateway URLs or rewrite Agent/workspace configuration files.
- **Agent model relay**: `/control/agent-relay` starts/stops a separate loopback server with a per-start token; enabled models are addressed as `messenger/<local-model-id>` to disambiguate providers, and matching formats are forwarded. Responses clients can also use Chat providers through a streaming converter that preserves function/custom tools and reasoning summaries; unsupported features fail visibly. The Chat/Responses/Messages/Interactions matrix supports streaming text, reasoning summaries and function calls. Unsupported stateful or hosted-tool features fail explicitly. Built-in ACP profiles opt into per-process `providerTakeover` (default off); All three built-in ACP agents can select enabled models in any of the four Provider formats. Relay credentials go to the spawned process; provider credentials stay in Core, and user configuration files are not rewritten. OpenCode takeover probes the configured executable with --version through the platform process host and injects the appropriate V1 or V2 provider schema with model-specific native adapters (all four formats in V2; V1 Interactions retains relay conversion); failed or unsupported probes prevent startup. Existing workers retain their startup configuration.
