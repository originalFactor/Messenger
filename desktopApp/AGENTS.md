# desktopApp — Desktop (JVM) application shell

Thin `org.jetbrains.kotlin.jvm` + `compose.multiplatform` + `kotlin.compose` shell over `shared`. `Main.kt` is the entry point (constructs `AppContainer` directly) and `compose.desktop { application { … } }` defines the native distribution formats (`Dmg`/`Msi`/`Deb`).

- Version name comes from the root `VERSION`; the native package version is `rootProject.ext["packageVersion"]` = `MAJOR.MINOR.<commitCount>` (jpackage/MSI requires a numeric, strictly increasing `ProductVersion`).
- ProGuard is ENABLED in release (`proguard { isEnabled = true; obfuscate = false; optimize = true }`), with rules in `desktopApp/proguard-rules.pro` plus JetBrains' `default-compose-desktop-rules.pro`. Obfuscation stays off: Compose Desktop/Skiko/JNA resolve classes by name. Kept surface: the lifecycle-only UniFFI/JNA bridge, kotlinx.serialization lookup, Coil/Ktor service-loader targets, OkHttp's optional TLS providers and the `llm-typewriter`/RaTeX runtime classes. Do not add business FFI methods. The `main` entry point is already kept by the plugin's generated root config.
- **`@JvmMultifileClass` keep rule is load-bearing**: ProGuard's `method/specialization/returntype` optimization corrupts multifile parts (Guardsquare/proguard#533, CMP-10488) — it rewrites a method's return type but not the `checkcast` in its body, so the build stays green and the app dies at runtime with `java.lang.VerifyError: Bad return type`. JetBrains' `default-compose-desktop-rules.pro` only keeps `**Kt__*` (facade ending in `Kt`); a `@JvmName` facade such as okio's `Okio__OkioKt` slips through, and `Okio.buffer()` is hit on the first DataStore read. `proguard-rules.pro` adds `-keep,allowshrinking,allowobfuscation class **__*Kt { *; }` — **never remove it**, and re-verify after a ProGuard or Compose upgrade. The failure surfaces only as jpackage's generic **"Failed to launch JVM"** dialog: the JVM starts fine, `main` throws, and the launcher reports it as a JVM launch failure — so always test `packageRelease*` output, never just a green build.
- Platform actuals live in `shared/src/desktopMain` (PowerShell/`/bin/sh` shell executor, FileDialog image pickers, the Swing `JFileChooser` folder picker, clipboard/toast). `Main.kt` opens the store with `CoreHandle.open`, starts `startHttpServer(0u)`, installs `RestCoreBridge(localAddr, token)` and stops the server on window close. `:core-bindings-desktop` is a compile dependency of BOTH `desktopApp` and `shared`, but exposes lifecycle only.
- **Undecorated window + taskbar**: `Main.kt` creates the window with `undecorated = true`, so AWT has no native frame to fit into the desktop work area and Windows maximizes it over the taskbar. `DesktopWindow.kt` (`WorkAreaMaximizedBounds()`) sets `Frame.maximizedBounds` to the current monitor's bounds minus `Toolkit.getScreenInsets()` and re-applies it when the window changes monitor. `maximizedBounds` is only a hint applied at maximize time — setting it while already maximized does nothing — so the effect must be installed before any maximize (title-bar button, Win+Up, double-click).
- Desktop CI builds ONE artifact today: Windows x86_64 (MSI) on `windows-latest`. The Windows ARM64 zipped app image and the Linux x86_64/ARM64 `.deb` matrix entries exist but are COMMENTED OUT in `build-desktop.yml` (since `8f0e38f`, no hardware to verify them); re-enable them as-is if that changes (each builds on its own-architecture runner, so the host `cargo build` needs no extra Rust target).
- Desktop CI installs a Rust toolchain (`dtolnay/rust-toolchain@stable`) plus `Swatinem/rust-cache`: `:core-bindings-desktop` runs `cargo build --profile bindgen -p messenger-ffi` and `uniffi-bindgen` on the host, so cargo is on the critical path of every `:desktopApp` task. Only the small lifecycle surface is generated. Only the HOST target is needed — no `--target`, no cargo-ndk, no NDK.
- Desktop CI runs with `ANDROID_HOME` pointed at an EMPTY directory (no Android package is needed to build the JVM app) and therefore passes `-Pmessenger.buildRuntimeNative=false`: `:runtime`'s `externalNativeBuild` block would otherwise make AGP resolve an NDK at configuration time and fail the build before any task runs. Anything that configures `:runtime` without an NDK installed needs that flag.
- **MSI on a machine without WiX**: `packageReleaseMsi` needs WiX 3.11. If `WIX_PATH` is unset it downloads `wix311-binaries.zip` (~34 MB) itself and caches it at `~/.gradle/compose-jb/wix311.zip`. A download interrupted mid-flight leaves a **truncated zip that Gradle keeps reusing**, so every later run dies with `Task :unzipWix FAILED — Cannot expand ZIP '<home>/.gradle/compose-jb/wix311.zip'` and nothing about the message says "corrupt cache". Fix: delete that file and rerun (the plugin re-downloads it); check with `unzip -t <file>` — integrity must report no errors, and the real archive is ~34.6 MB (a ~1 MB file is a truncation). Setting `WIX_PATH` to an existing WiX 3.11/3.14 `bin` skips the download entirely, as CI does.

```bash
./gradlew-cli :desktopApp:run
./gradlew-cli :desktopApp:packageReleaseMsi   # Windows (CI uses windows-latest + .\gradlew.bat)
./gradlew-cli :desktopApp:packageReleaseDmg   # macOS
./gradlew-cli :desktopApp:packageReleaseDeb   # Linux
```

- Desktop native distributions use platform-specific icons in `src/main/resources`: `icon.ico` for Windows, `icon.icns` for macOS, and `icon.png` for Linux; the running window uses `logo.png`. Keep these packaging assets in sync when changing the application icon.
