# shared — KMP library


## Source sets

- `commonMain` — target-agnostic. MUST NOT reference `java.*` or any JVM-only artifact; one such reference breaks the Android/Desktop build.
- `jvmSharedMain` — Android + Desktop only: `OkioStorage`, `okio.FileSystem.SYSTEM`, the on-disk preferences DataStore, `RestCoreBridge` and the `LocalStores.jvmShared.kt` factory for `RustCloudFacade`. Tests for it live in `jvmSharedTest` (uses `org.junit`/`runBlocking`, not available on the JVM common target).
- The hierarchy is manual (`dependsOn` edges `commonMain` ← `jvmSharedMain` ← `androidMain`/`desktopMain`, `commonTest` ← `jvmSharedTest` ← `desktopTest`): the default Kotlin hierarchy template cannot express the Android+Desktop grouping, so root `gradle.properties` sets `kotlin.mpp.applyDefaultHierarchyTemplate=false`. Keep both the `dependsOn` calls and that property.
- The `compose.resources` block stays in `shared` (strings under `composeResources/values[-zh-rCN]/`).

## DI

Manual DI via `di/AppContainer.kt` (constructs all repositories/data sources). Android: `MessengerApplication` constructs it; Desktop: `Main.kt` constructs it. Both install it in `AppContainerHolder` before UI startup. Wear constructs its own repository/bridge in `WearMessengerApplication` and does not depend on `shared`. Never reintroduce `MessengerApplication.initRepositories()`.

## Storage (Rust core — no Room)

There is **no Room database and no Kotlin entity/DAO layer**. Android and Desktop run the Rust core (the TUI has a separate Core-backed profile; Wear uses the phone): `providers`, `models`, `agents`, `projects`, `conversations`, `messages`, `sync_meta` and `kv` live in the core's SQLite store (`core/rust/crates/messenger-store`, schema v7, columns mirror the old Room names). App shells call `CoreHandle.open` only for store/import startup, then `startHttpServer(0u)` and install `RestCoreBridge(localAddr, token)` into `CoreBridgeRegistry`. All repositories use `/api/v1`; the native bridge exposes no business calls.

Key columns to know: `models.contextWindow/inputRate/outputRate/cacheReadRate/cacheWriteRate/inputModalities/outputModalities/supports*`; `models.metadata/metadataOverrides`; `agents.role/toolsEnabled/toolsFollowDefault/toolsConfig/description`; `conversations.contextSummary*/contextTokens*/overrideToolsEnabled/overrideToolsConfig/writable/projectId`; `providers.apiFormat`. Schema changes belong in `messenger-store`, not here.

## Navigation & adaptive UI

- `Screen.kt` sealed class routes (`createRoute()`), `NavGraph.kt` destinations, `BottomLevelRoutes.kt` for bottom-nav routes. Nav arguments read via `backStackEntry.arguments?.read { getStringOrNull("key") }` (CMP SavedState API).
- **Page transitions**: `NavGraph` wires NavHost transitions from `presentation/navigation/PageTransitions.kt`; each `Screen` has an order in `RouteOrders` (grouped by bottom-nav branch), later = slide in from right/bottom, earlier = reversed; pops add fade and follow the predictive-back gesture on Android.
- **In-screen sub-pages** (e.g. `CloudServerScreen` inside `CloudSettingsScreen`, tool-config overlays) are state-hosted, not routes, and register `presentation/platform/BackHandler` (expect/actual → `PredictiveBackHandler` on Android, requires manifest `enableOnBackInvokedCallback`; no-op on Desktop).
- **Adaptive layout**: `MainScaffold` uses `BoxWithConstraints` + `windowSizeClassFor()` — Compact (< 600 dp) = fixed full-width bottom `NavigationBar`, Medium/Expanded = edge-attached `NavigationRailBar`. The parent scaffold consumes the bottom navigation slot and its system-bar inset, so top-level screens do not reserve a separate navigation clearance.
- **Conversations FAB**: one `FloatingActionButtonMenu` (M3 Expressive) holds "New chat" and "New project"; do not stack a second small FAB next to it. New chats from the home FAB/picker are plain (no project) and therefore land in the `No project` folder. The menu adds `fabMenuExpanded` (BackHandler collapses it, multi-select clears it) and a full-size transparent click layer above the list for tap-outside dismissal. The menu's own 16 dp horizontal/bottom padding is cancelled with an equal opposite offset (mirrored in RTL) so the FAB keeps the Scaffold's standard 16 dp margin.
- **Agents FAB**: matches Chats with `FloatingActionButtonMenu`, animated `ToggleFloatingActionButton` and labelled New Agent / Agent Market items (Market requires Cloud login). Match the RTL-aware 16 dp menu-padding offset; tap outside or Back collapses it, and entering multi-select clears and hides it.
- **Dual-pane (non-Compact)**: `NavGraph` renders `*DualPaneScreen` (list left / detail right) for Conversations, Agents, Providers, Settings instead of pushing detail routes. Selection state is `rememberSaveable`. **A Compose `key(...)` around the detail pane does NOT create a new `viewModel()`**: the default ViewModel key is only `ViewModelProvider.DefaultKey:<class>`, so the right pane reuses the first instance for every selection. Detail ViewModels whose target can change must therefore expose a `load<X>(id)` that retargets their flows (e.g. `ProjectConversationsViewModel.loadFolder` also decides the `projectId` written by its "new chat", `AgentConversationsViewModel.loadAgent`) and the screens call it from `LaunchedEffect(id)`; only per-target ViewModels that never need switching (Chat, ConversationSettings) may keep the id in the constructor.
- **Settings stays two-pane** on Desktop/tablets: the left Settings list stays visible and all Provider navigation (list → models → model details or Provider editor) replaces the right pane through `ProvidersSinglePaneScreen`. Do not nest `ProvidersDualPaneScreen` inside Settings; standalone Providers still uses its dual-pane layout. Both layouts share the same state-hosted Provider navigation and single-pane Back returns through model → Provider → list → Settings placeholder.
- Non-Compact extras: right-click context menus (`components/ContextMenu.kt`), hover background, `TooltipBox` on rail/app-bar icons. Long-press multi-select uses `components/MultiSelectTopBar.kt` (Conversations, Agents).
- `ProviderEdit`/`AgentEdit` use optional-parameter routes; `AgentMarket*` routes require a signed-in Cloud user. `ProviderEditScreen` carries the protocol dropdown (`providers_api_format_label`).

## Network / API

- Native business requests go through `CoreBridge` → `jvmSharedMain/core/RestCoreBridge` → the authenticated loopback `/api/v1` service. Provider wire requests, model discovery, reasoning replay and usage parsing are owned by Rust (`messenger-http`, `messenger-core`, `messenger-llm`, `messenger-sync`). `Provider.apiFormat` selects `CHAT` / `RESPONSES` / `MESSAGES` / `INTERACTIONS` / `AUTO`; AUTO resolves to CHAT for direct native requests. Kotlin still contains `OpenAiClient`, protocol codecs and DTOs under `data/remote`, with codec tests, but they are not the native chat orchestration path.
- **Reasoning formats**: Rust `messenger-llm` decodes provider reasoning into `<think>` blocks and `messenger-core` persists the detected `Conversation.reasoningFormat`. History replay is protocol-aware: full `reasoning_content` can be restored, `think_tag` retained, and `reasoning_summary` stripped. Keep the Kotlin codec tests consistent when changing the shared wire semantics.
- **Multimodal**: Kotlin `ContentPartCodec` (`data/local/ContentPartCodec.kt`) serializes text/images into `partsJson`; Rust builds provider wire content. Android downscales images to the configured 1568 px limit, applies EXIF rotation and caches PNGs in `filesDir/chat_images/`; Desktop caches the original bytes and MIME type. `RustMessageRepository` delegates local image cleanup to `ChatImageStore`.
- **Image cloud sync**: each image part in `partsJson` is `{type:"image", dataUri, localPath}` with the full base64 `dataUri`. The server stores `partsJson` verbatim (byte-identical round-trip — never strip/re-encode/reorder server-side); on pull, the core's `messenger_sync::rehydrate` recreates missing local files from `dataUri` under a deterministic `sync_{sha256(...)}` name (idempotent).
- Wear chat is forwarded to the phone over WebSocket (see `wear/AGENTS.md`); the watch never calls providers directly.

## Cloud client (`data/cloud/`)

- `RustCloudFacade` delegates every call to the core's sync engine (`core/rust/crates/messenger-sync`): session cookie, per-account cursor, paged delta pull, tombstone application, push of pending upserts/deletes, market and card APIs. Kotlin keeps only the 750 ms debounce, the `syncError` StateFlow, the `localChangesEnabled` gate and the cookie-aware Ktor client Coil uses for avatars. `CloudUser` carries optional SaaS fields (`role`, `aiApiKey`, `quotaBalance`, `quotaExpiresAt`, `displayName`).
- **Marking a change must schedule the push**: `requestLocalChange()` writes the pending upsert/delete into the core's queue **and then calls `requestLocalSync()`**, which is the only thing that drains it (750 ms debounce). Marking without scheduling leaves the edit queued forever, so the change never leaves the device. The gate must also be open, or marking is skipped entirely: it is opened by login/register/`completeLogin`, by a successful `sync()`/`upload()`/`downloadAndRestore()`, **and in the facade's `init` when a session was restored from the core's kv** — a restarted app is still signed in, and before that fix every edit after a restart was silently dropped.
- **The Rust turn loop bypasses the repositories**: `runTurn` writes the assistant/tool rows straight into the core, so `RustMessageRepository`'s change hook never fires. Callers of `runTurn` must flag the conversation themselves when the turn ends (`ChatViewModel`'s `finally`, and `MobileWearChatHandler` after the loop); without it a reply is on disk but never uploaded. The HTTP turn task updates `lastMessage` from the final persisted row; Kotlin observes the resulting store event.
- **Manual sync actions are not the only path**: `AppContainer.initializeLocalAndCloudData()` pulls once at startup, so a device only receives another device's edits at launch. There is no periodic poll — pulling is otherwise manual (`CloudSettingsScreen` restore) or implied by a local push.
- **Sync progress is acked to the server**: the core sends `ack = <stored sync cursor>` on every `/api/sync` call, which is how the server knows when a deleted conversation/agent/provider/project's tombstone is no longer needed by any device and can be purged. Nothing to do in Kotlin — but never make the engine echo the request's `since` as the ack (a post-push pull asks from a version the client has not applied).
- **Server-rejected sessions sign the app out** (`sessionExpired`): the server keeps session state, so a `401` on an authenticated call means the session is gone (revoked on another device, expired after 30 days, account deleted) — it never recovers. The Rust engine turns that `401` into `CloudError::SessionExpired` and drops the stored cookie/user (`SyncEngine::with_session`, which every authenticated call goes through except the two password-gated endpoints, whose `401` means a wrong current password); the facade notices "we were signed in, the core now has no user" (`detectRejectedSession`) and does logout's local cleanup, raising `CloudFacade.sessionExpired`. `SettingsScreen` toasts `cloud_settings_session_expired` once, `CloudSettingsScreen` shows the sign-in form because `user` is null, and `acknowledgeSessionExpired()` clears the flag. A `401` from login/register stays a credential error and must NOT sign anyone out.
- **Builtin cloud provider**: on login/`/me` refresh the client persists `aiApiKey` and idempotently seeds a local Provider with reserved ID `BUILTIN_PROVIDER_ID = "builtin-messenger-cloud-ai"` pointing at `{serverUrl}/v1`. It is excluded from cloud sync both ways, ignored by `hasLocalData()`, removed on logout/deletion/server-URL change, and hidden from edit/delete in `ProvidersScreen`. Its model list auto-syncs from `GET {server}/v1/models` (idempotent: preserves row ids and `isEnabled`, deterministic ids for new models, forced on reseed/empty table, otherwise hourly — failures never block). The built-in catalog is read-only (including model enable state): its UI exposes only Sync and read-only model details, with no add/delete/multi-select/context editing actions. Manual Sync calls `CoreBridge.cloudSyncBuiltinModels(force = true)` directly, refreshing all existing rows and Cloud metadata from Messenger Extended Models Protocol `/v1/models`; never route built-in Sync through general discovery, selection/import, or models.dev.
- **Restore from cloud is a rebuild, not a delta**: `downloadAndRestore()` → `core.cloudSync(replaceLocal = true)` re-reads the whole account (`since = 0`) because the stored cursor describes the rows the wipe just deleted; pulling from the cursor emptied the Agents list and dropped the server-seeded default Agent. A signed-in store with no default Agent triggers the same full re-read, so devices damaged by the old behaviour self-heal on the next sync.
- **Built-in title agent** `Agent.BUILTIN_TITLE_AGENT_ID = "builtin-title-agent"` ("标题生成" literal) is seeded only when no title-role holder exists (`ensureBuiltinTitleAgent()`, called at startup / after full sync / `clearAllDataAndReinit`); excluded from sync like the builtin provider.
- **Built-in agent display names are localized**: the seeded rows keep their literals (`默认 Agent` / `标题生成`, plus the historical English values) because sync and the local-data baseline compare rows, never names. The UI renders them through `presentation/utils/AgentDisplayName.kt` (`Agent.displayName()` / `resolvedDisplayName()` / `agentDisplayNames()`): an *unrenamed* builtin (`isDefault` or the reserved title ID, **and** a seed literal) shows `agent_builtin_default_name` / `agent_builtin_title_name`; anything the user typed — including a user Agent that took over the title role — shows verbatim. The Agent editor shows the localized label but keeps submitting the stored literal unless the field is actually edited, so "open and save" never counts as a rename.
- Avatars: multipart upload to the avatar endpoints; GETs are authenticated proxies, downloaded during sync into `filesDir/cloud_avatars` so `AgentAvatar` is purely file-based.
- **The signed-in user avatar is cloud-owned**: `RustCloudFacade.refreshUser` / `login` / `register` run `syncUserAvatar`, which caches `CloudUser.avatarUrl` via `cloudCacheAvatar` into the `userAvatar` preference and records `userAvatarSyncKey` = `userId|avatarUrl#avatarVersion`. The key (not the version alone) is the change detector — the proxy URL is identical for every account, so signing into a second account on the same device must re-download. A null remote avatar deletes the cached file (how the web user center's removal reaches the app), and a device's own upload passes `keepLocalFile` so it keeps the picked file instead of re-downloading byte-identical bytes. `SettingsViewModel.setUserAvatar` is the only writer that also uploads; never set the preference directly.
- Cloud settings UI (`CloudSettingsScreen`): account card (the web user center's `displayName` when present, else the email), plan card (aggregate balance + per-entitlement rows), card-key redemption (preview → confirm → redeem), sync/security sections; the server URL lives in the `CloudServerScreen` sub-page. The plan card derives the balance from `quotaEntitlements` when the aggregate fields are absent (older servers), and the screen re-pulls `/me` on entry (`SettingsViewModel.refreshCloudUser()`) — quota is server-side live state, and a cached `CloudUser` snapshot must never be the only source.
- **Session/quota snapshot invariants**: the session cookie lives only in the core's kv (`cloud_session` + `cloud_session_host`); `AppPreferences.cloudSession*` is a leftover of the removed Ktor cookie jar and MUST NOT gate startup refresh or default-Agent seeding (use `cloud.user` / the core session instead). `/api/auth/{login,register,me}` all return the same full user shape (quota + `aiApiKey`), and `completeLogin`/`downloadAndRestore` re-refresh the snapshot so a freshly logged-in account never renders 0 quota.

- **Local Cloud development discovery**: `CloudServerScreen` offers an explicit discovery action via `data/cloud/DevServerDiscovery` (common expect / JVM actual). UDP query `messenger-cloud-discover-v1` on port 53319 targets loopback and interface broadcasts; replies provide HTTP ports. Credential-free `/api/dev/discovery` verification requires `{service:"messenger-cloud",version:1,development:true}`. Loopback and Android emulator host `10.0.2.2` also probe ports 3000–3005. Discovery only fills the draft; Save uses the existing server/session reset flow. No persistent background scanning.

## Chat features

- **Context auto-summarization (80%)**: Rust `messenger-core/src/agent.rs` performs the non-stream summary call at the declared context-window threshold, preserving the last 10 sent messages. It stores `contextSummary` / `contextSummaryUntil` without rewriting visible history and records per-round usage. Summary failure emits an error event but the send continues. `context.rs::build_api_context_messages` caps assembled request history at 20 messages, including when a context window is known; keep changes to this policy in Core.
- **Agent roles**: `Agent.role` is `chat` (default) / `title`, plus the `isDefault` boolean. Regular/Default/Title Generator pickers in `AgentEditScreen`; Default and Title are single-holder roles — claiming one demotes the previous holder (`AgentEditViewModel.save()`). `RustAgentRepository.delete` blocks only the default Agent; deleting the title holder (the built-in included) re-seeds a builtin title agent through `cloudEnsureBuiltinTitleAgent()`, because the invariant is "exactly one title generator", not "this row is permanent". `clone` resets role (the built-in is clonable too). `Agent.description` is display-only and never sent to the model. All "select agent" pickers filter out title-role agents.
- **Title generation**: Rust `messenger-core/src/agent.rs::generate_title_if_needed` runs before the terminal `Finished` event for still-untitled conversations with a non-blank assistant reply. The HTTP layer supplies title configuration only when the title Agent has a model binding; the loop then uses that configuration, sanitizes and caps the title, and re-reads before saving to preserve a manual rename. Failure emits `TitleFailed` and falls back to the first user message. There is no Kotlin `ConversationTitleGenerator` service.
- **Empty-conversation cleanup**: the rule lives in the Rust core (`messenger_core::conversation`, see `core/rust/AGENTS.md`) and is reached through `CoreBridge.sweepEmptyConversations(excludeIdsJson)` → `ConversationRepository.sweepEmptyConversations`. Kotlin owns only the trigger: the three chat-list screens call it from a `LaunchedEffect` on entry, and `ConversationsScreen` passes the dual-pane's selected conversation id so the open chat is never deleted from under the user. Deletes record their cloud tombstone inside the core.
- **Tool calling**: built-in `terminal` + `WorkspaceTool` (glob/grep/read/edit/create) via expect/actual `executeShellCommand` / `executeWorkspaceOperation`. Grep delegates to bundled ripgrep 14.1.1 (output contract `path:line:text` with NUL-terminated paths; `--hidden --no-ignore -g '!.git'`). Tool arguments are NEVER pre-screened — enforcement is sandbox-based (Android: companion UID; desktop: user process); reads are unrestricted, writes are declaration-gated by mode. `ChatTool.writeAccess` classifies write tools. Desktop shell = PowerShell (UTF-8) or `/bin/sh`, cwd = workspace; 60 s timeout kills the process. Android routes through the `:runtime` companion — NO fallback shell (absent companion ⇒ empty tool list).
- **Agent mode (read-only/writable)**: toggled in the `+` bottom panel (`ChatInputBar`), stored PER-CONVERSATION (`Conversation.writable`). Mode only changes the DECLARED tools (write tools + unrestricted terminal description in writable mode); tools execute automatically in both modes (no confirmation dialogs). Turn-time decisions read the DB row, never the `agentWritable` StateFlow. MCP tools are mode-agnostic. The panel shows the entry only when the platform supports built-in tools (`builtinChatToolsSupported()`); never gate it on `createBuiltinChatTools(null)`, which is the no-project declaration gate and is empty on every platform.
- **Agent tool config**: per-Agent master + per-tool switches (`toolsEnabled` / `toolsConfig`, absent key = enabled) with the swipe takeover gesture for `toolsFollowDefault`; conversations can override via `overrideToolsEnabled` / `overrideToolsConfig`. A request carries `tools` when the effective master switch is on AND the platform registry is non-empty — `supportsToolCalling` metadata is deliberately NOT a gate.
- **Agent loop**: `ChatViewModel.generateResponse` sends the operation/content/selected message group through `RestCoreBridge.runTurn`. Rust admits the turn before transcript mutation, persists assistant/tool rows, rebuilds context and owns the loop until final text / API error / cancellation. Kotlin executes `ToolCallRequested` using the platform tool map and posts results to `/turns/tools/{callId}/result`. Tool history is stored in `partsJson` (`ContentPart.ToolCall/ToolResult`); provider request conversion lives in `messenger-llm`, not a Kotlin repository.
- **Model discovery and overrides**: `ProviderDetailViewModel` uses Core discovery/metadata APIs. Provider metadata and models.dev enrichment live in `messenger-sync`; schema v7 keeps imported `metadata` separate from explicit `metadataOverrides`. Built-in cloud models use Cloud-supplied metadata. The TUI applies its own pi-catalog fallback (see `tui/AGENTS.md`).
- **Model list rates**: model rows and the discovery picker omit context-window badges. The rate badge orders input / cache read / cache write / output (`Ix1.0 Rx1.0 Wx1.0 Ox1.0`, at least one and at most two decimal places), retaining unknown cache rates as `—`; only four explicit zeros display Free. `ChatModel.cacheWriteRate` maps to the nullable Core v7 `models.cacheWriteRate` column and `/v1/models` `cache_write_rate`.
- **MCP inventory**: Kotlin `domain/mcp/McpManager` maintains configured server connections and active tools. App shells set `RestCoreBridge.platformTools = container::availableTools` and publish the inventory for Core device-control turns; platform stdio implementations live under Android/Desktop source sets.
- **History paging**: `ChatHistoryPager` loads recent/older pages for platforms with `paginateChatHistory`; `RestCoreBridge.listMessagesByConversationJson` follows all REST pages when callers request the complete history. Do not treat the first API page as the entire transcript.

## Chat rendering


- Android and Desktop render Markdown/code/LaTeX with `cc.ptoe:llm-typewriter` through the `ChatMarkdownText` expect/actual. Android uses a Compose `LazyColumn`; Desktop uses `ChatDocumentBubble`. Raw assistant Markdown travels as `ChatBlock.RawMarkdown` so tool cards and text retain turn order. Do not reintroduce `:renderer-android`, native DocumentHandle, or a native LaTeX engine.
- **`MarkdownTypewriterRenderer` paints the state's buffer, not its `text` argument**: it calls `state.revealedTokens()` and ignores the string it is handed, so a settled (`isStreaming = false`) message must be rendered from a state seeded with the message (`appendToken` + `completeSource` + `skipToEnd`) — rendering it from a fresh, never-seeded state draws an empty bubble while the row still measures correctly. Both `ChatMarkdownText` actuals do this; keep them in sync (the files are otherwise identical), and keep `ChatBubbleContentTest` (desktop) green — it asserts a finished reply paints its text.
- `ChatViewModel` exposes `streamingContent` / `streamingMessageId` StateFlows. `RestCoreBridge.runTurn` consumes chat SSE, forwards events, executes requested tools and emits `stream_ended` if no terminal event arrives.
- `RestCoreBridge.subscribe` starts the `/events` SSE feed lazily on the first listener and keeps it open for the process lifetime (reconnecting after a 1 s backoff). It is deliberately never cancelled from Kotlin — the core closes it when the server stops. `HttpServerHandle.stop` is a suspending graceful stop, so it must never be awaited on a UI thread (see `desktopApp/AGENTS.md`).
- An agent turn collapses into one `ChatListItem.ToolGroupItem` (tool rounds → results → final text, placeholder-row-first included); ERROR placeholders stay standalone; orphan TOOL rows render as standalone cards. Wear bypasses ChatViewModel and never runs tools.

## Design language (Material 3 Expressive)

- M3 Expressive (reference: InstallerX-Revived). Theming in `presentation/theme/Theme.kt`: static light/dark + Material You dynamic color, `ExpressiveShapes` (10–32 dp), `ExpressiveTypography`, `MaterialExpressiveTheme` + `MotionScheme.expressive()` (`@OptIn(ExperimentalMaterial3ExpressiveApi::class)` — NOT `ExperimentalMaterial3Api`).
- UI rules: consume theme tokens (`shapes`/`colorScheme`/`typography`) — no ad-hoc `RoundedCornerShape` for shapes a token covers (one-offs like chat bubble tails excepted); prefer spring motion over linear tweens for spatial transitions; prefer expressive component variants (contained loading indicator, `MaterialShapes`).
- **Settings entries**: every `ListItem` carries a `title` (feature name only) and a `subtitle` (purpose-only description — no implementation/style detail).

## Editing guides

- **New screen**: add route to `Screen.kt` → destination in `NavGraph.kt` → composable under `presentation/ui/<feature>/` → ViewModel in `presentation/viewmodel/` → (bottom-level routes) `BottomLevelRoutes.kt`.
- **New local API endpoint**: add the Rust handler and OpenAPI/event contract in `messenger-http` → expose it through `CoreBridge` / `RestCoreBridge` → repository/facade → ViewModel. Keep `{code,message,detail}` failures visible. Provider protocol changes belong in `messenger-llm`; Kotlin DTO/codec changes alone do not alter native chat requests.

## ACP and remotely started turns

- **ACP Agents** is a list with structured add/edit dialogs (description, stdio command, JSON arguments/environment and optional cwd), seeded once with Codex, Claude Code and OpenCode templates. Remote Control lives inside Messenger Cloud settings; saving either section fetches the current control settings to preserve the other fields. ACP and MCP add actions use the shared `IntegrationFab` (Manual add / Store); the Store requires a Cloud session and loads curated templates through Core `controlCommand(action="store",kind="acp"|"mcp")`. There is no separate ACP Chat settings item or chat toolbar dialog. The project New Conversation picker combines normal Agents and enabled ACP profiles; the home picker contains only normal Agents, and Core rejects projectless ACP creation. ACP session IDs (`acp:`) render `AcpConversationScreen` through `ChatScreen`, with Markdown, streaming, tools, permission choices, cancellation and paged history. Core exposes their local transcripts in normal conversation listings; they never enter Cloud sync. `RestCoreBridge` publishes available built-in and MCP tools and serves Core-requested tools over the event feed.
- Send, retry, and regenerate pass the content or selected message group to Core before mutating the transcript. Dropping the initiating SSE cancels only its turn. The phone's Wear bridge uses the same admission path with tools disabled.

- **ACP chat parity and settings**: `AcpChatMessages` projects text/thought/tool events into the normal `Message`/`ChatListItem` model and `ChatMessageList` on both platforms; use the same bubbles, avatars, input insets, paging and empty state. `allowMessageMutation=false` retains copy menus but hides ACP-unsupported individual delete/regenerate/retry actions. ACP loads settings on entry and shows Agent-provided model, effort, mode and boolean controls in the normal composer’s plus panel. Settings open as a separate full-page Scaffold. ACP supports image/file pickers and clipboard attachments, Agent command suggestions, context usage beside Send, an in-screen FIFO queue during generation and long-press Send / queued-message Steer. Queue dispatch preserves the editable draft; failures pause automatic dispatch. Steering uses Core’s explicit injected/promptRequired outcome. The settings page uses labeled exposed dropdown fields, tonal switch list items with a single accessible toggle target, Expressive contained loading, an icon back action and a centered 840 dp content limit. Quick selectors use compact dropdowns so large model catalogs do not bury effort controls. The chat Settings button hosts `AcpSessionSettingsScreen`, reading Agent-provided grouped select/boolean options and legacy modes via Core `sessionSettings` / `setSessionConfig`. Replace values only from Agent responses/updates; disable controls during requests and prompts.
