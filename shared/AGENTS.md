# shared — KMP library

All shared Android/Desktop/Web logic. Clean Architecture: `domain/` (pure Kotlin models + repository interfaces), `data/` (Rust-core repositories, network, repository impls), `presentation/` (Compose UI + ViewModels), `di/` (manual DI).

## Source sets

- `commonMain` — target-agnostic. MUST NOT reference `java.*` or any JVM-only artifact; one such reference breaks the whole web target.
- `jvmSharedMain` — Android + Desktop only: `OkioStorage`, `okio.FileSystem.SYSTEM`, the on-disk preferences DataStore, and the `RustCloudFacade` factory. Tests for it live in `jvmSharedTest` (uses `org.junit`/`runBlocking`, not available on wasm).
- `androidMain` / `desktopMain` / `wasmJsMain` — platform `actual` implementations.
- The hierarchy is manual (`dependsOn` edges `commonMain` ← `jvmSharedMain` ← `androidMain`/`desktopMain`, `commonTest` ← `jvmSharedTest` ← `desktopTest`): the default Kotlin hierarchy template cannot express the Android+Desktop-but-not-wasm grouping, so root `gradle.properties` sets `kotlin.mpp.applyDefaultHierarchyTemplate=false`. Keep both the `dependsOn` calls and that property.
- The `compose.resources` block stays in `shared` (strings under `composeResources/values[-zh-rCN]/`).

## DI

Manual DI via `di/AppContainer.kt` (constructs all repositories/data sources). Android: `MessengerApplication` owns it (`MessengerApplication.instance`); Desktop: `Main.kt` constructs it; `wear` mirrors the pattern. Never reintroduce `MessengerApplication.initRepositories()`.

## Storage (Rust core — no Room)

There is **no Room database and no Kotlin entity/DAO layer**. Every platform runs the Rust core: `providers`, `models`, `agents`, `projects`, `conversations`, `messages`, `sync_meta` and `kv` live in the core's SQLite store (`core/rust/crates/messenger-store`, schema v3, columns mirror the old Room names). `AppContainer` requires `CoreBridgeRegistry.bridge` and wires the `Rust*Repository` implementations; the entry points open the store (`CoreHandle.open`, with the legacy Room file passed as `legacy_db_dir` for the one-shot import).

Key columns to know: `models.contextWindow/inputRate/outputRate/cacheReadRate/inputModalities/outputModalities/supports*`; `agents.role/toolsEnabled/toolsFollowDefault/toolsConfig/description`; `conversations.contextSummary*/contextTokens*/overrideToolsEnabled/overrideToolsConfig/writable/projectId`; `providers.apiFormat`. Schema changes belong in `messenger-store`, not here.

## Navigation & adaptive UI

- `Screen.kt` sealed class routes (`createRoute()`), `NavGraph.kt` destinations, `BottomLevelRoutes.kt` for bottom-nav routes. Nav arguments read via `backStackEntry.arguments?.read { getStringOrNull("key") }` (CMP SavedState API).
- **Page transitions**: `NavGraph` wires NavHost transitions from `presentation/navigation/PageTransitions.kt`; each `Screen` has an order in `RouteOrders` (grouped by bottom-nav branch), later = slide in from right/bottom, earlier = reversed; pops add fade and follow the predictive-back gesture on Android.
- **In-screen sub-pages** (e.g. `CloudServerScreen` inside `CloudSettingsScreen`, tool-config overlays) are state-hosted, not routes, and register `presentation/platform/BackHandler` (expect/actual → `PredictiveBackHandler` on Android, requires manifest `enableOnBackInvokedCallback`; no-op on Desktop).
- **Adaptive layout**: `MainScaffold` uses `BoxWithConstraints` + `windowSizeClassFor()` — Compact (< 600 dp) = bottom `NavigationBar`, Medium/Expanded = `NavigationRailBar`. The floating bottom nav exists only in Compact; its 92 dp clearance is published as `LocalBottomNavClearance` (default 0) and consumed by top-level screens' FAB/list padding.
- **Conversations FAB**: one `FloatingActionButtonMenu` (M3 Expressive) holds "New chat" and "New project"; do not stack a second small FAB next to it. New chats from the home FAB/picker are plain (no project) and therefore land in the `No project` folder. The menu adds `fabMenuExpanded` (BackHandler collapses it, multi-select clears it) and a full-size transparent click layer above the list for tap-outside dismissal. The menu's own 16 dp horizontal/bottom padding is cancelled with an equal opposite offset (mirrored in RTL) so the FAB keeps the Scaffold's standard 16 dp margin.
- **Dual-pane (non-Compact)**: `NavGraph` renders `*DualPaneScreen` (list left / detail right) for Conversations, Agents, Providers, Settings instead of pushing detail routes. Selection state is `rememberSaveable`.
- Non-Compact extras: right-click context menus (`components/ContextMenu.kt`), hover background, `TooltipBox` on rail/app-bar icons. Long-press multi-select uses `components/MultiSelectTopBar.kt` (Conversations, Agents).
- `ProviderEdit`/`AgentEdit` use optional-parameter routes; `AgentMarket*` routes require a signed-in Cloud user. `ProviderEditScreen` carries the protocol dropdown (`providers_api_format_label`).

## Network / API

- Ktor + SSE client. `Provider.apiFormat` (`ApiFormat` in `domain/model/Provider.kt`) selects the provider's conversation protocol: `CHAT` (OpenAI Chat Completions, default), `RESPONSES`, `MESSAGES` (Anthropic), `INTERACTIONS` (Gemini), or `AUTO` (the built-in Messenger proxy follows the caller's protocol; `requestFormat` resolves it to CHAT for direct calls). `OpenAiClient` picks the path (`/chat/completions`, `/responses`, `/messages`, `/interactions`) plus `x-api-key`/`x-goog-api-key` headers, encodes via `data/remote/format/ApiFormatRequests.kt`, and decodes into the same `ChatStreamEvent` flow and `ChatCompletionResponseDto` — Chat Completions still uses `data/remote/sse/ChatStreamParser`, the other three use `data/remote/format/ApiFormatStreamParser`. DTOs in `data/remote/dto/`.
- **Reasoning formats**: every protocol's decoder wraps reasoning into `<think>` blocks; the Chat Completions parser distinguishes the source field (`reasoning_content` = full CoT, `reasoning` = summary), while the Responses/Messages/Interactions decoders always report `reasoning_summary`. `ChatStreamParser` wraps both `delta.reasoning_content` (full CoT, format `"reasoning_content"`) and `delta.reasoning` (reasoning summary, format `"reasoning_summary"`) into `<think>` blocks. The first detected format is persisted to `Conversation.reasoningFormat` and mirrored via cloud sync; `buildRequestMessages` replays history accordingly (`reasoning_content` restores think tags into the field, `think_tag` keeps tags as-is, `reasoning_summary` strips reasoning entirely — never send reasoning fields to those gateways).
- **Multimodal**: `ChatMessageDto.content` is a `JsonElement` (legacy string or OpenAI `[{type,text|image_url}]` array); `ApiRepositoryImpl` picks the shape from `Message.hasImages`. Images are downscaled to 1568 px, EXIF-rotated, cached as PNG under `filesDir/chat_images/`, reaped on delete.
- **Image cloud sync**: each image part in `partsJson` is `{type:"image", dataUri, localPath}` with the full base64 `dataUri`. The server stores `partsJson` verbatim (byte-identical round-trip — never strip/re-encode/reorder server-side); on pull, the core's `messenger_sync::rehydrate` recreates missing local files from `dataUri` under a deterministic `sync_{sha256(...)}` name (idempotent).
- Wear chat is forwarded to the phone over WebSocket (see `wear/AGENTS.md`); the watch never calls providers directly.

## Cloud client (`data/cloud/`)

- `RustCloudFacade` delegates every call to the core's sync engine (`core/rust/crates/messenger-sync`): session cookie, per-account cursor, paged delta pull, tombstone application, push of pending upserts/deletes, market and card APIs. Kotlin keeps only the 750 ms debounce, the `syncError` StateFlow, the `localChangesEnabled` gate and the cookie-aware Ktor client Coil uses for avatars. `CloudUser` carries optional SaaS fields (`role`, `aiApiKey`, `quotaBalance`, `quotaExpiresAt`, `displayName`).
- **Marking a change must schedule the push**: `requestLocalChange()` writes the pending upsert/delete into the core's queue **and then calls `requestLocalSync()`**, which is the only thing that drains it (750 ms debounce). Marking without scheduling leaves the edit queued forever, so the change never leaves the device. The gate must also be open, or marking is skipped entirely: it is opened by login/register/`completeLogin`, by a successful `sync()`/`upload()`/`downloadAndRestore()`, **and in the facade's `init` when a session was restored from the core's kv** — a restarted app is still signed in, and before that fix every edit after a restart was silently dropped.
- **The Rust turn loop bypasses the repositories**: `runTurn` writes the assistant/tool rows straight into the core, so `RustMessageRepository`'s change hook never fires. Callers of `runTurn` must flag the conversation themselves when the turn ends (`ChatViewModel`'s `finally`, and `MobileWearChatHandler` after the loop); without it a reply is on disk but never uploaded, and `ChatViewModel` must also refresh the conversation's `lastMessage` preview from the persisted rows (the list would otherwise keep showing the user's own message).
- **Manual sync actions are not the only path**: `AppContainer.initializeLocalAndCloudData()` pulls once at startup, so a device only receives another device's edits at launch. There is no periodic poll — pulling is otherwise manual (`CloudSettingsScreen` restore) or implied by a local push.
- **Sync progress is acked to the server**: the core sends `ack = <stored sync cursor>` on every `/api/sync` call, which is how the server knows when a deleted conversation/agent/provider/project's tombstone is no longer needed by any device and can be purged. Nothing to do in Kotlin — but never make the engine echo the request's `since` as the ack (a post-push pull asks from a version the client has not applied).
- **Server-rejected sessions sign the app out** (`sessionExpired`): the server keeps session state, so a `401` on an authenticated call means the session is gone (revoked on another device, expired after 30 days, account deleted) — it never recovers. The Rust engine turns that `401` into `CloudError::SessionExpired` and drops the stored cookie/user (`SyncEngine::with_session`, which every authenticated call goes through except the two password-gated endpoints, whose `401` means a wrong current password); the facade notices "we were signed in, the core now has no user" (`detectRejectedSession`) and does logout's local cleanup, raising `CloudFacade.sessionExpired`. `SettingsScreen` toasts `cloud_settings_session_expired` once, `CloudSettingsScreen` shows the sign-in form because `user` is null, and `acknowledgeSessionExpired()` clears the flag. A `401` from login/register stays a credential error and must NOT sign anyone out.
- **Builtin cloud provider**: on login/`/me` refresh the client persists `aiApiKey` and idempotently seeds a local Provider with reserved ID `BUILTIN_PROVIDER_ID = "builtin-messenger-cloud-ai"` pointing at `{serverUrl}/v1`. It is excluded from cloud sync both ways, ignored by `hasLocalData()`, removed on logout/deletion/server-URL change, and hidden from edit/delete in `ProvidersScreen`. Its model list auto-syncs from `GET {server}/v1/models` (idempotent: preserves row ids and `isEnabled`, deterministic ids for new models, forced on reseed/empty table, otherwise hourly — failures never block).
- **Restore from cloud is a rebuild, not a delta**: `downloadAndRestore()` → `core.cloudSync(replaceLocal = true)` re-reads the whole account (`since = 0`) because the stored cursor describes the rows the wipe just deleted; pulling from the cursor emptied the Agents list and dropped the server-seeded default Agent. A signed-in store with no default Agent triggers the same full re-read, so devices damaged by the old behaviour self-heal on the next sync.
- **Built-in title agent** `Agent.BUILTIN_TITLE_AGENT_ID = "builtin-title-agent"` ("标题生成" literal) is seeded only when no title-role holder exists (`ensureBuiltinTitleAgent()`, called at startup / after full sync / `clearAllDataAndReinit`); excluded from sync like the builtin provider.
- **Built-in agent display names are localized**: the seeded rows keep their literals (`默认 Agent` / `标题生成`, plus the historical English values) because sync and the local-data baseline compare rows, never names. The UI renders them through `presentation/utils/AgentDisplayName.kt` (`Agent.displayName()` / `resolvedDisplayName()` / `agentDisplayNames()`): an *unrenamed* builtin (`isDefault` or the reserved title ID, **and** a seed literal) shows `agent_builtin_default_name` / `agent_builtin_title_name`; anything the user typed — including a user Agent that took over the title role — shows verbatim. The Agent editor shows the localized label but keeps submitting the stored literal unless the field is actually edited, so "open and save" never counts as a rename.
- Avatars: multipart upload to the avatar endpoints; GETs are authenticated proxies, downloaded during sync into `filesDir/cloud_avatars` so `AgentAvatar` is purely file-based.
- **The signed-in user avatar is cloud-owned**: `RustCloudFacade.refreshUser` / `login` / `register` run `syncUserAvatar`, which caches `CloudUser.avatarUrl` via `cloudCacheAvatar` into the `userAvatar` preference and records `userAvatarSyncKey` = `userId|avatarUrl#avatarVersion`. The key (not the version alone) is the change detector — the proxy URL is identical for every account, so signing into a second account on the same device must re-download. A null remote avatar deletes the cached file (how the web user center's removal reaches the app), and a device's own upload passes `keepLocalFile` so it keeps the picked file instead of re-downloading byte-identical bytes. `SettingsViewModel.setUserAvatar` is the only writer that also uploads; never set the preference directly.
- Cloud settings UI (`CloudSettingsScreen`): account card (the web user center's `displayName` when present, else the email), plan card (aggregate balance + per-entitlement rows), card-key redemption (preview → confirm → redeem), sync/security sections; the server URL lives in the `CloudServerScreen` sub-page. The plan card derives the balance from `quotaEntitlements` when the aggregate fields are absent (older servers), and the screen re-pulls `/me` on entry (`SettingsViewModel.refreshCloudUser()`) — quota is server-side live state, and a cached `CloudUser` snapshot must never be the only source.
- **Session/quota snapshot invariants**: the session cookie lives only in the core's kv (`cloud_session` + `cloud_session_host`); `AppPreferences.cloudSession*` is a leftover of the removed Ktor cookie jar and MUST NOT gate startup refresh or default-Agent seeding (use `cloud.user` / the core session instead). `/api/auth/{login,register,me}` all return the same full user shape (quota + `aiApiKey`), and `completeLogin`/`downloadAndRestore` re-refresh the snapshot so a freshly logged-in account never renders 0 quota.

## Chat features

- **Context auto-summarization (80%)**: when the model declares `contextWindow > 0`, a projected context at 80% folds all sent messages older than the last 10 into a summary (non-stream call) stored on the conversation (`contextSummary` + `contextSummaryUntil`), injected at request time as a leading SYSTEM message — the UI history is never modified. Per-round usage is recorded after `Done` (exact for the builtin provider, estimates otherwise). Failures show a snackbar but never block the send. Fallback without a context window: `takeLast(20)`.
- **Agent roles**: `Agent.role` is `chat` (default) / `title`, plus the `isDefault` boolean. Regular/Default/Title Generator pickers in `AgentEditScreen`; Default and Title are single-holder roles — claiming one demotes the previous holder (`AgentEditViewModel.save()`). `AgentRepositoryImpl.delete` blocks only the default Agent; deleting the title holder (the built-in included) re-seeds a builtin title agent through `cloudEnsureBuiltinTitleAgent()`, because the invariant is "exactly one title generator", not "this row is permanent". `clone` resets role (the built-in is clonable too). `Agent.description` is display-only and never sent to the model. All "select agent" pickers filter out title-role agents.
- **Title generation**: on the first non-blank stream `Done`, `ConversationTitleGenerator.launchGenerateIfNeeded` (Mutex-serialized, fire-and-forget) titles "untitled" conversations using the title holder's prompt/model; strips think blocks/quotes/newlines, caps length; re-reads before writing (never clobbers a manual rename or summary state). Failure surfaces a localized error and falls back to truncating the first user message.
- **Empty-conversation cleanup**: the rule lives in the Rust core (`messenger_core::conversation`, see `core/rust/AGENTS.md`) and is reached through `CoreBridge.sweepEmptyConversations(excludeIdsJson)` → `ConversationRepository.sweepEmptyConversations`. Kotlin owns only the trigger: the three chat-list screens call it from a `LaunchedEffect` on entry, and `ConversationsScreen` passes the dual-pane's selected conversation id so the open chat is never deleted from under the user. Deletes record their cloud tombstone inside the core.
- **Projects (a project IS a workspace)**: only project conversations may call workspace-bound tools (terminal + glob/grep/read/edit/create); a plain conversation declares none. `createBuiltinChatTools(workspaceRoot)` registers NOTHING for `null` (no platform fallback). `ChatViewModel.resolveWorkspaceFor(conv)` reads a FRESH DB row (never the `WhileSubscribed` project StateFlow). The model is told the cwd via `TurnRequest.workspace_note`. Deleting a project keeps its conversations (they become plain; `ON DELETE SET NULL`). Chat lists show a Recent Chats shortcut above the folders: the last `ConversationsViewModel.RECENT_CONVERSATION_LIMIT` conversations as jump-only rows (`recentChatSection` → `ConversationListItem(showActions = false)`), then one row per project and a `No project` folder holding every plain conversation (`ProjectListItem.projectSection` + `UnprojectedFolderItem`). The shortcut carries no rename/delete/switch-Agent menu, so each conversation still has exactly one management surface. `ProjectConversationsScreen` is the folder page and takes `projectId = null` for the no-project folder (`Screen.UnprojectedConversations`). Folder pages support long-press multi-select (batch delete / switch Agent). Projects sync as their own collection and are applied BEFORE conversations on pull. Android workspace calls are brokered per-call over AIDL with an explicit `root` (see `runtime/AGENTS.md`).
- **Tool calling**: built-in `terminal` + `WorkspaceTool` (glob/grep/read/edit/create) via expect/actual `executeShellCommand` / `executeWorkspaceOperation`. Grep delegates to bundled ripgrep 14.1.1 (output contract `path:line:text` with NUL-terminated paths; `--hidden --no-ignore -g '!.git'`). Tool arguments are NEVER pre-screened — enforcement is sandbox-based (Android: companion UID; desktop: user process); reads are unrestricted, writes are declaration-gated by mode. `ChatTool.writeAccess` classifies write tools. Desktop shell = PowerShell (UTF-8) or `/bin/sh`, cwd = workspace; 60 s timeout kills the process. Android routes through the `:runtime` companion — NO fallback shell (absent companion ⇒ empty tool list).
- **Agent mode (read-only/writable)**: toggled in the `+` bottom panel (`ChatInputBar`), stored PER-CONVERSATION (`Conversation.writable`). Mode only changes the DECLARED tools (write tools + unrestricted terminal description in writable mode); tools execute automatically in both modes (no confirmation dialogs). Turn-time decisions read the DB row, never the `agentWritable` StateFlow. MCP tools are mode-agnostic.
- **Agent tool config**: per-Agent master + per-tool switches (`toolsEnabled` / `toolsConfig`, absent key = enabled) with the swipe takeover gesture for `toolsFollowDefault`; conversations can override via `overrideToolsEnabled` / `overrideToolsConfig`. A request carries `tools` when the effective master switch is on AND the platform registry is non-empty — `supportsToolCalling` metadata is deliberately NOT a gate.
- **Agent loop** (`ChatViewModel.launchChatTurn`): a `Done` with tool calls persists an assistant row, executes each call (persisting `role=TOOL` rows, `NonCancellable` interrupted marker on cancel), rebuilds context, and continues until final text / API error / cancel — unbounded rounds. Tool turns round-trip through `partsJson` (`ContentPart.ToolCall/ToolResult`, codec in `data/util/ContentPartCodec.kt`); `buildRequestMessages` maps them to OpenAI `tool_calls` / `role:"tool"` messages and drops leading orphan TOOL rows.
- **MCP**: `ToolsSettingsScreen` manages MCP servers (DataStore `mcp_servers_json`, `McpManager`); transports are stdio (Desktop `ProcessBuilder`, Android via `:runtime` AIDL `startMcpProcess`/`sendMcpInput`/`stopMcpProcess`) and SSE/HTTP (Ktor). `AppContainer.availableTools` aggregates built-in + MCP tools. `CoreBridge.runTurn` takes a `suspend` tool executor: Android/Desktop bridge it into the synchronous UniFFI callback with `runBlockingCall`, wasm hands Rust a `Promise` (`ToolHost` is `async_trait(?Send)` on wasm32) so remote MCP calls work without blocking the event loop.

## Chat rendering

- Android: `:renderer-android` native Views (`RecyclerView` + `MessageView` + `DocumentView`) consuming Rust `DiffBatch` streams; Desktop: `DesktopDocumentBubble` / `DesktopDocumentView` Compose blocks keyed by `block.id`. LaTeX via the RaTeX engine (no italic; serif); code highlighting via Rust syntect.
- **Bubble width (Desktop/Web)**: `ChatDocumentBubble` (commonMain) sizes the bubble to its content with `Modifier.width(IntrinsicSize.Max)` and applies the Android row insets (`start = 8.dp`, `end = 64.dp`). The document blocks all `fillMaxWidth()`, so without the intrinsic pass every bubble spans the whole pane no matter how short the reply; without the trailing inset a long reply runs into the pane edge. The avatar row is bottom-aligned with the bubble and the timestamp sits BELOW that row (as in Android's `MessageView`, where it is outside `contentRow`): inside the row, the timestamp made the row's tallest child bubble + label, pushing the 32dp avatar ~16 dp below the bubble's bottom edge and burying the 4 dp tail corner. Regression tests: `ChatDocumentBubbleWidthTest` (desktopTest) pins the width, the right margin and the avatar/bubble bottom alignment.
- `ChatViewModel` exposes `streamingContent` / `streamingMessageId` StateFlows (SSE `Content` appends; reset on completion).
- An agent turn collapses into one `ChatListItem.ToolGroupItem` (tool rounds → results → final text, placeholder-row-first included); ERROR placeholders stay standalone; orphan TOOL rows render as standalone cards. Wear bypasses ChatViewModel and never runs tools.

## Design language (Material 3 Expressive)

- M3 Expressive (reference: InstallerX-Revived). Theming in `presentation/theme/Theme.kt`: static light/dark + Material You dynamic color, `ExpressiveShapes` (10–32 dp), `ExpressiveTypography`, `MaterialExpressiveTheme` + `MotionScheme.expressive()` (`@OptIn(ExperimentalMaterial3ExpressiveApi::class)` — NOT `ExperimentalMaterial3Api`).
- UI rules: consume theme tokens (`shapes`/`colorScheme`/`typography`) — no ad-hoc `RoundedCornerShape` for shapes a token covers (one-offs like chat bubble tails excepted); prefer spring motion over linear tweens for spatial transitions; prefer expressive component variants (contained loading indicator, `MaterialShapes`).
- **Settings entries**: every `ListItem` carries a `title` (feature name only) and a `subtitle` (purpose-only description — no implementation/style detail).

## Editing guides

- **New screen**: add route to `Screen.kt` → destination in `NavGraph.kt` → composable under `presentation/ui/<feature>/` → ViewModel in `presentation/viewmodel/` → (bottom-level routes) `BottomLevelRoutes.kt`.
- **New stored entity**: schema + CRUD in `core/rust/crates/messenger-store` → FFI/wasm export → `CoreBridge` (+ the three platform bridges) → domain model → `Rust*Repository` → wire into `AppContainer`.
- **New API endpoint**: DTOs (`data/remote/dto/`) → `OpenAiClient` method → repository interface → `ApiRepositoryImpl` → handle `HttpException` via `extractHttpErrorMessage()`.
