# tui — Python terminal client

- Use Python 3.11+, Textual and Poetry 2. Run `poetry -C tui install` to install the dependencies from `poetry.lock` into `.venv`.
- Run `poetry -C tui run python workflow.py dev` to build and launch. `build` builds the debug Core. `test` runs the Rust API suite, Python/Core chat and Cloud integration tests, workspace-tool tests, and Textual headless keyboard tests (`tests/test_tui.py`, `test_cloud.py`, `test_tools.py`).
- The workflow uses Cargo's reported executable path and the regular build cache. `release` builds the optimized Core, tests it, and stages the locked Python runtime dependencies in an isolated Poetry environment. It creates a host tarball in `dist/` using the Core version and supports `--out PATH`.
- `messenger_tui/__main__.py` owns startup and shutdown. `core.py` owns the stdio handshake and authenticated REST/SSE transport. Keep the loopback bearer token off command lines and out of logs.
- Resolve the startup directory and select its nearest enclosing local project. Prompt before creating a project for an unknown directory, and continue in standalone mode when trust is declined. Core stamps the project with the local device ID. New chats carry the active project ID, and `/sessions` only lists chats in the active project or standalone scope.
- `/project` creates or opens a local project in standalone mode. Inside a project it edits the name or workspace folder, or leaves the project for a fresh standalone session. Reopening an existing folder reuses its project ID. Editing preserves the device owner and history.
- `model_metadata.py` owns the cached pi.dev capability fallback, `cloud.py` owns account and built-in-model provisioning helpers, and `tools.py` owns the local tool executor. `chat.py` owns turn state, persistence calls, conversation uploads and history. `app.py` and `screens.py` own the Textual layout, composer, and dialogs. Slash completion shares the command catalog with the command palette.
- `/providers` lists, adds, edits, and deletes providers through the Core API. Saving a new provider opens its model manager and discovers models automatically. **Manage models** opens the same view for an existing provider. Discovery adds missing IDs and refreshes metadata from the provider's Messenger `/models` extensions with pi-catalog as a field-wise fallback. Save user overrides separately and retain them during refresh. Allow manual model management even when discovery fails. `/connect` still selects the model entered in the wizard and then fetches additional models.
- Core deletes the associated models with a provider. Clear the active model after deleting it or its provider. If the active model is disabled, abort sends before creating a conversation or changing messages.
- `/cloud` manages the Messenger Cloud account and base URL. Sign-in provisions Messenger Cloud AI and syncs its catalog through Core. Older signed-in profiles are provisioned or have their model metadata backfilled when opening `/providers` or `/models`. The built-in provider displays only Cloud-supplied metadata. Keep those fields read-only and change enablement with the separate Core endpoint. Sign out of the old server before saving a different URL. Keep login passwords and API keys out of terminal output.
- After a terminal turn event, upload the saved standalone conversation through Core. `/sync` uploads eligible older local conversations and retries failed uploads. Core binds each uploaded conversation to the current Cloud server and account. Show upload failures and conflicts in the transcript and status without replacing the local reply.
- The dedicated store defaults to `~/.messenger/tui.db`. Use `--db PATH` for a test or separate profile and `--core PATH` for a custom executable. The running TUI reads the product version from `/meta`; `--version` asks the Core binary for `--version` without starting the HTTP server. `--workspace PATH` overrides the startup directory; the dev workflow captures the caller's directory before switching into `tui`.
- `/tools` sets the conversation's tool override (off, inspection, or writable), including before its first send. It requires a trusted project; standalone conversations declare no workspace tools. New sessions inherit the Agent policy until explicitly overridden. Core retains ownership of effective Agent policy and built-in declarations; the default Agent starts with tools disabled. Persist overrides through the conversation API, never force tools on for every request.
- `tools.py` executes local terminal/glob/grep/read/edit/create requests in the active project's workspace and returns results through Core. Terminal execution uses the user's permissions, like Desktop; inspection mode guides terminal behavior and excludes edit/create, but is not an OS sandbox. Search requires `rg` on PATH. Bound command time/output and file reads, terminate subprocess groups on cancellation, and return explicit tool errors. Remote-owned workspace calls stay routed by Core.
- Retain the draft until Core accepts the turn. Show chat failures in the transcript and status line. Never silently retry. Close active chat streams on exit.
- Verify terminal input in a PTY and run chat integration against a temporary database and mock provider.
